## 一、我的判断：看到了什么、根问题是什么

### 1. 数据总览

| 指标 | 数量 | 占比 |
|---|---|---|
| 提交请求总数 | 1060 | 100% |
| 选课成功（select_success=1） | 907 | 85.6% |
| 余量不足失败（select_success=0） | 103 | 9.7% |
| 超时未回传（select_success 为空） | 50 | 4.7% |

### 2. 关键发现：失败与「前端余量信息的滞后时长」强相关，与其他因素弱相关

对每条请求计算余量信息的滞后时长：

```
滞后时长 = request_time - balance_synced_at
```

即学生点击提交时，前端展示的那份「剩余名额」已经多久没跟服务端同步过了。

| 滞后时长 | 请求数 | 失败数 | 失败率 |
|---|---|---|---|
| ≤ 8 分钟 | 680 | 25 | 3.7% |
| 8–15 分钟 | 23 | 2 | 8.7% |
| 15–20 分钟 | 24 | 8 | 33.3% |
| 20–30 分钟 | 55 | 14 | 25.5% |
| 30–60 分钟 | 196 | 54 | 27.6% |

失败率在滞后超过 15 分钟后从约 4% 陡升到 26%–33%。
**103 次失败中，有 76 次（73.8%）发生在余量信息滞后超过 15 分钟时。**

对照组（说明「真凶」不是别的维度）：

- **展示余量 `display_seats` 几乎不预测失败**：展示为 0 的请求失败率仅 12.9%，展示为 1–2 的失败率 20%，展示为 20–30 的失败率也有 9.4%——并不是「看着余量少就失败多」，因为展示的数字本身可能是旧的。
- **并发量 `qps_instant` 只有弱相关**：失败率从低并发（≤40）的 6.5% 升到高并发（>80）的 13.9%，远不如滞后时长的区分度。
- **校区、课程类别**失败率分布在 5.6%–12.8%，均匀无热点，说明是系统性机制问题而非某类课程问题。

### 3. 根问题

**前端展示的「尚有余量」是十几到几十分钟前的旧快照，与服务端真实余量不同步。** 学生看到余量还在，点击提交时服务端真实名额早已归零，于是大量提交以「余量不足」失败；学生只得反复刷新、焦虑重试。

（补充观察：50 条超时未回传与并发量弱相关，qps 61–80 时超时率 8.5%，属独立的服务端性能问题，不计入本结论。）

## 二、做了什么

设计并评估一条**数据驱动、按口径可量化的改善规则**：

> 当客户端余量信息滞后时长 **≥ 15 分钟** 时，不再把展示的「尚有余量」当作可信信号，而是主动标记该课程为「名额紧张」并强制重新同步（或提示学生先刷新）后再允许提交。

用「失败=90s / 标记=15s」的口径，把每条提交的最终结果（成功/失败/超时）代入，对滞后阈值（0–3600s 逐值）以及「滞后阈值 × 展示余量阈值」的组合做了全量扫描，选出净收益最大的阈值。结果见 `analyze.py` 输出。

## 三、怎么证明有用（数据算出的数字）

以推荐的「滞后 ≥ 15 分钟」规则为例：

| 结果 | 数值 |
|---|---|
| 被标记的请求数 | 283（占全部 26.7%） |
| 拦截的失败数（TP） | 77 / 103 = **74.8%** |
| 误标（本会成功的请求被标记） | 189 |
| 被标记的超时请求 | 17（保守计入 15s 标记成本） |
| 净收益 | 77 × 90 − 283 × 15 = 6930 − 4245 = **2685 秒** |
| 总损失 | 9270 秒 → 6585 秒，**减少 29.0%** |

也就是说：只标记约四分之一的请求，就拦下四分之三的余量不足失败，总损失下降近三成。

阈值稳健性：数据精确最优阈值在 960 秒（16 分钟），净收益 2715 秒（减少 29.3%），与 15 分钟规则几乎一致，说明结论不依赖于某个精确秒数，落在「滞后超过 15 分钟」这一档即可。

### 可复现步骤

```bash
# 依赖：仅 Python 3 标准库
python -I analyze.py
```

脚本输出三部分：① 按滞后时长的失败率分段；② 纯滞后阈值与「滞后×展示余量」组合阈值的净收益 Top 扫描；③ 推荐规则（滞后 ≥ 900s）的标记数、拦截失败数、净收益与成本降幅。README 中所有数字均可由该脚本复现。

### 假设说明（非数据，需明确标注）

- 假设「标记名额紧张 / 强制同步」能可靠阻止被标记请求的失败——这正是口径给「标记」定价 15s、给「失败」定价 90s 的含义。
- 超时未回传（select_success 为空）不计入 90s 失败损失；若被标记仍计 15s 标记成本，属保守估计。

## 附：更根本的改善方向（供后续评估）

标记规则是对症缓解；根因是同步间隔过长。若服务端能承受，把余量同步周期压到 5–10 分钟以内（或对低余量课程做服务端推送），可直接消除大部分滞后，是比「事后标记」更彻底的方案。数据支持这一判断：滞后 ≤ 8 分钟的 680 条请求失败率只有 3.7%。
